# Device 模块创建

为当前 `stm32-hal-devices` 仓库创建简单、可直接移植的外设驱动。用户的明确要求优先于本技能中的默认约定。

## 开始前

先读取当前仓库的 `config.h`、`README.md`、同类型模块，以及用户指定的参考工程。用户已经提供型号、接口、引脚、API 或可运行参考代码时，直接使用这些信息，不再重复确认。

信息优先级如下：

1. 用户指定且已经运行正常的参考工程
2. CubeMX 生成代码和芯片/模块官方资料
3. 当前仓库的同类型模块
4. 必要的最小假设

参考工程已有寄存器值、时钟、总线宽度、GPIO 模式或初始化顺序时，逐项保留，不主动优化、替换或调整。只有缺失信息会影响硬件行为且无法从现有代码确认时，才向用户询问。

## 实现原则

- 采用完成需求所需的最简单结构，避免不必要的分层、对象封装、回调和状态机。
- 优先移植已经验证的代码；不要重写可直接复用的底层初始化和寄存器配置。
- 不修改用户提供的参考工程，只在当前仓库写入结果。
- 模块默认放在仓库根目录的 `<Module>/`。用户指定扁平目录时，所有模块文件直接放在该目录，不创建子目录。
- 只公开应用层真正需要的 API；可保留容量、状态、底层读写等直接有用的接口。
- 第三方源码必须保留版权声明、原始注释和配置；只做目录适配、编译开关或必要接口连接。
- 不声称硬件已验证。能编译则执行与改动相称的编译；没有完整工程时执行静态检查，并明确说明验证范围。

编写文件时读取 [代码与 README 模板](./references/templates.md)。

## 集成要求

### 模块代码

- 自有头文件使用 include guard，紧接着包含 `config.h`，主体用 `#if DEVICE_<MODULE>` 包裹。
- 自有 `.c` 第一行包含对应头文件，主体用 `#if DEVICE_<MODULE>` 包裹。
- 模块参数放在模块 `.h`；硬件句柄、引脚控制和可调硬件映射放在 `config.h`。
- API 使用 `模块名_动作()`；禁止新增 `s_`、`g_` 前缀。
- 自有函数使用现有仓库的 Doxygen 注释格式，并保持 4 空格缩进。
- 保留章节分隔块；正式代码的注释只描述功能和约束，不记录调试过程。
- 上游第三方文件不强制改写成仓库注释样式。

### config.h

- 新模块的 `DEVICE_<MODULE>` 默认值为 `0`。
- 配置节放在最终 `#endif` 之前。
- 依赖 HAL 句柄时包含 CubeMX 生成的对应头文件。
- 从已运行工程移植的时钟、寄存器和总线参数必须原值复制，并在 README 中同步记录。

### README.md

更新目录、项目结构和完整模块章节。章节至少包含简介、图片占位、硬件连接、CubeMX 配置、`config.h`、API 和使用示例。

- 标题格式为 `N. <型号或模块名> <类型名>模块`，不重复堆叠 I2C、SPI、UART、ADC 等技术前缀。
- 图片编号跟随 README 最近模块实际采用的命名方式；不要改动旧图片编号。只预留 Markdown 图片路径，不创建伪图片。
- CubeMX 参数必须来自参考工程或官方资料，并明确哪些值需要保持一致。
- 示例优先展示用户指定的应用层 API，保持短小并能直接复制。
- 新章节放在“联系方式”等尾部章节之前，并以 `---` 与其他模块分隔。

## 完成检查

- `DEVICE_<MODULE>` 默认关闭，所有自有源码在关闭时仍可参与工程编译。
- 目录层级和文件数量符合用户要求。
- 应用层 API、参数类型和返回值在 `.h`、`.c`、README 中一致。
- 没有改变参考工程中的硬件配置值和关键初始化顺序。
- README 的目录链接、项目结构、图片占位和示例均已更新。
- 没有覆盖或整理任务无关的用户改动。
